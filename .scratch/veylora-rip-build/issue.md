# Veylora RIP Entire Project Build Specification

## Problem Statement

The project needs a native Windows DTF RIP for one converted Epson ET-8550 configuration. The current planning documents establish the product direction, feature requirements, competitive reference points, and architectural implementation sequence, but they are distributed across a PRD, requirements specification, competitive analysis, and implementation plan.

The build needs one coherent specification that an implementation agent can execute without losing the project's core constraints:

- Veylora must generate its own printer-ready output.
- Digital Factory, AcroRIP, PrintFab, and other commercial RIPs may be research references but must not be runtime dependencies.
- Logical channels such as C, M, Y, K, and W must remain distinct from physical slots and protocol channels.
- White output must be independently generated, supplied, inspected, calibrated, allocated, and screened.
- The final screened device raster and retained printer artifact must be inspectable.
- Large jobs must render deterministically with bounded memory, cancellation, and disk-space checks.
- Jobs must preserve immutable provenance and avoid duplicate printing after ambiguous failures.
- Physical printer evidence must determine whether the native backend is accepted.

The first milestone is not a feature-rich UI. It is a repeatable pressed transfer produced from bytes generated by Veylora RIP for one verified converted ET-8550 setup.

## Solution

Build Veylora RIP as a Rust workspace with a deterministic, headless rendering core and thin adapters for persistence, diagnostics, CLI operation, Windows transport, and a Tauri 2 desktop shell. The frontend uses TypeScript, Svelte, Bits UI, and Vite+ as its unified Vite-based toolchain, with pnpm as the declared package manager.

The implementation will proceed in gates:

1. Establish the workspace, domain vocabulary, IDs, hashes, errors, provenance, and test baseline.
2. Record the actual converted ET-8550 setup and represent logical, physical, and protocol channels separately.
3. Build diagnostic targets and a native-protocol investigation CLI before production UI.
4. Define immutable DeviceSetup, PrintMode, Recipe, JobSnapshot, artifact, and SubmissionAttempt models.
5. Implement bounded PNG import, metadata policy, ICC/color boundaries, physical layout, and gang-sheet state.
6. Implement CMYK and independent white separation, supplied masks, curves, choke/spread, knockout, clear masks, white-slot allocation, calibration, screening, and disk-backed band rendering.
7. Implement an ET-8550 encoder and deterministic file sink before Windows transport.
8. Implement the Windows spooler adapter with explicit lifecycle and ambiguous-submission handling.
9. Validate independent channels, geometry, feed, orientation, deposition order, repeatability, and pressed output on the physical printer.
10. Add calibration, measurement records, quality baselines, preflight, queue recovery, diagnostics, portable jobs, CLI workflows, and the Tauri desktop application.
11. Add clean installation, schema migration, support bundles, licensing records, and update safety only after the personal production workflow is validated.

The highest-level test seam is the headless application-service workflow:

`JobSnapshot -> preflight -> bounded render -> logical planes -> physical-slot rasters -> screened device raster -> retained printer artifact -> SubmissionAttempt`

This seam must work with a file sink and fake transport in automated tests. The real Windows transport and converted ET-8550 are introduced only at the physical native-backend gate.

## Implementation Decisions

### Product and scope

- The product is Veylora RIP, positioned as “Native control for every printed layer.”
- The initial target is one converted Epson ET-8550 configuration, one cut-sheet film setup, and one eventually validated PrintMode and Recipe.
- Personal high-end DTF output is the first user outcome. Small-shop operation and distribution are future validation targets.
- Digital Factory and AcroRIP are benchmark references only. They are not runtime dependencies and their advertised behavior is not treated as proof of parity.
- The first product milestone is a repeatable pressed transfer generated from Veylora-owned printer-ready bytes.
- Accounts, cloud services, payments, subscriptions, DRM, remote telemetry, broad printer support, rolls, multi-lane production, industrial throughput, and automatic printer maintenance are out of the first release.

### Architecture

- Use a Rust workspace with a platform-independent domain layer and one-way dependencies.
- Use separate modules for domain models, image import, color management, layout, separation, screening, bounded rendering, device configuration, encoding, transport, persistence, diagnostics, CLI, application services, and UI.
- The domain layer must not depend on Windows, a UI toolkit, a database, or a specific decoder.
- The UI must not directly own rendering, separation, encoding, persistence, or Windows APIs.
- The encoder consumes validated physical-slot raster bands and must not perform hidden color management or white generation.
- The file sink is a first-class backend and precedes the Windows device sink.
- The output inspector reads retained stage artifacts rather than recomputing a preview.

### Domain contracts

- `LogicalChannel`, `PhysicalSlot`, and `ProtocolChannel` are distinct concepts.
- `DeviceSetup` describes one physical conversion and its evidence, including identity, firmware observation, map, slots, ink, film, feed, and verification state.
- `PrintMode` is an immutable tested bundle of raster, protocol, channel, deposition, media, geometry, and quality behavior.
- `Recipe` references calibration, profiles, white policy, screening, ink limits, and finishing conditions.
- `JobSnapshot` is immutable once rendering begins and contains all output-affecting references and provenance.
- `SubmissionAttempt` is append-only and records one transport attempt with intended and written byte counts, status, timing, and evidence.
- `Ambiguous submission` is a first-class state. It must be reviewed and never automatically retried.
- `Logical plane`, `Physical-slot raster`, `Screened device raster`, and encoded printer artifact are separate inspection stages.

### Device and protocol

- Device verification requires labeled physical channel tests.
- No inferred or imported map can become production-ready without evidence.
- Duplicate white slots use explicit allocation rules and must not receive accidental full duplicate coverage.
- The protocol specification must document framing, page structure, bands, compression, checksums when used, channel order, and end-of-job behavior.
- Only protocol fields established by evidence may be implemented as supported behavior.
- Unknown or unsupported controls must be rejected or marked experimental rather than silently ignored.
- Windows blocking print calls run behind a worker and transport interface.

### Input and color

- Initial artwork input is SDR PNG truecolor or truecolor with alpha.
- Embedded ICC and explicit sRGB signaling are supported according to declared metadata precedence.
- Untagged RGB uses a visible configurable sRGB assumption.
- Separate grayscale white masks are first-class aligned assets.
- HDR, APNG, malformed profiles, unsupported color types, excessive dimensions, and unsafe resource use are rejected or explicitly warned.
- Color conversion uses a maintained external ICC/color-management engine behind an adapter. Native RIP means no commercial RIP dependency, not a requirement to invent an ICC engine.
- Source conversion occurs exactly once and records profile hashes, rendering intent, black-point compensation, library version, and overrides.
- Display proof is separate from device output conversion.

### White and separation

- White source choices are alpha, tonal generation, supplied mask, or disabled diagnostic mode.
- White policies are named and serializable.
- Supplied masks use explicit replace, union/max, intersection/min, or controlled blend semantics.
- White precedence is: source or automatic white, explicit combination, tonal response, choke/spread, clear-mask enforcement, calibrated slot allocation, and device screening.
- Custom white masks do not modify process alpha implicitly.
- Opaque white with zero CMYK remains eligible.
- Fully transparent pixels remain clear across every plane.
- White curves are named data, not only UI slider positions.
- White and process coverage have separate limits, with combined wet-load validation.
- Knockout and perforation masks are reversible and enforced as a final clear mask.

### Rendering and artifacts

- Rendering is deterministic, bounded, cancellable, and disk-space-aware.
- Large sheets use disk-backed bands and explicit halo handling for morphology.
- Screen phase is anchored to page coordinates so different band sizes do not create seams or different output.
- Stage artifacts and hashes are retained for logical planes, physical-slot rasters, screened rasters, and printer-ready output.
- Previews are labeled by stage and never presented as final device output.

### Persistence and lifecycle

- Local persistence uses a durable store with versioned schema migrations.
- Job snapshots are immutable; attempts are append-only.
- Lifecycle states explicitly distinguish rendering, readiness, submitting, submitted, ambiguous, failed, cancelled, review, and operator-confirmed completion.
- Restart recovery reconstructs outstanding attempts and never assumes that a transport failure means no paper moved.
- Selective reprints create new attempts linked to original placements and snapshots.

### UI and application services

- Application services orchestrate preflight, rendering, artifact retention, inspection, submission, review, and reprint.
- CLI and desktop UI use the same application-service contracts.
- UI controls are generated or gated from DeviceCapability and PrintMode support.
- The desktop shell is Tauri 2 with a TypeScript and Svelte frontend using Bits UI primitives wrapped by Veylora-owned components where product semantics, validation, styling, or accessibility behavior are needed.
- Vite+ is the frontend toolchain for development, checking, testing, building, and package-management delegation. pnpm is the declared package manager, and the package manifest and lockfile remain the dependency source of truth.
- The UI may be built first with clearly labeled fixture data, but fixture data and simulated previews must never be presented as physical printer output.
- Large rasters and printer artifacts remain Rust-managed. The frontend receives metadata, hashes, dimensions, status, and bounded preview tiles rather than full-resolution planes through ordinary IPC.

### Distribution foundations

- Portable job bundles contain assets, manifests, hashes, profiles, Recipes, and selected artifacts.
- Bundle extraction is path-safe and independent of original filesystem paths.
- Schema version and migration dispatch are required.
- Clean installation, compatibility documentation, dependency notices, and update rollback are distribution-readiness work, not first-use product requirements.

## Testing Decisions

### Primary test seam

The primary seam is the headless application-service workflow from an immutable JobSnapshot to a retained printer artifact and SubmissionAttempt. This is the highest useful seam because it exercises the real orchestration contract without requiring a desktop UI or physical printer.

The seam must support:

- A file sink that retains exact artifacts.
- A fake transport that can fail before, during, or after writing.
- A durable test store that can restart and reconstruct state.
- Deterministic fixtures for source assets, masks, DeviceSetup, PrintMode, Recipe, and expected artifacts.
- Explicit preflight findings and lifecycle transitions.

The physical transport is a separate integration seam. It consumes the same retained artifact and records actual Windows spooler and printer evidence.

### Test principles

- Test observable behavior and contracts, not private implementation details.
- Prefer the highest seam that can prove the behavior.
- Use lower-level unit tests for mathematical invariants, parser limits, mask algebra, geometry, calibration, and state transitions.
- Never treat a passing unit test, file-sink write, or Windows spooler success as proof of a usable transfer.
- Every physical acceptance claim must include actual setup, mode, Recipe, media, ink, film, press, cure, and observation records.
- Golden tests must explain whether a fixture is synthetic or captured reference evidence.
- Tests must be deterministic and must record output-affecting hashes.
- Frontend checks use Vite+ commands and cover Svelte component behavior, typed application-service integration, accessibility, keyboard navigation, and fixture-versus-physical-output labeling.

### Unit and contract tests

Test domain IDs, hashes, provenance, stable error codes, validation severity, lifecycle transition legality, immutable snapshots, PrintMode compatibility, white allocation, resource limits, and migration behavior.

Test image import for alpha ramps, hidden RGB under transparent pixels, opaque white, conflicting metadata, embedded profiles, HDR signaling, APNG, malformed profiles, unsupported color types, non-square PPI, and large decompression/resource cases.

Test color behavior for known values, untagged-source policy, profile precedence, no double-transform behavior, neutral and black policy, transform determinism, and explicit unsupported profile errors.

Test layout for physical dimensions, printable bounds, rotation, one-owner mirroring, crop offsets, gutters, duplicate semantics, alignment, and deterministic block nesting.

Test separation for white sources, mask combination, curves, choke/spread, opaque white with zero CMYK, transparent pixels, process/white independence, knockout, perforation, and clear-mask enforcement.

Test screening and rendering for calibration curves, channel limits, phase origin, band-size equivalence, cancellation, disk-full behavior, row halos, artifact hashes, and stage metadata.

Test encoding for framing, page geometry, channel order, band order, compression, end markers, unsupported settings, deterministic output, and golden stream comparison.

Test persistence for create/read, immutable snapshots, append-only attempts, schema migration, restart recovery, disk-full errors, corrupt stores, bundle round trips, safe extraction, and missing assets.

Test transport with fake failures before write, mid-write, after final write, timeout, cancellation, disconnect, and ambiguous outcome handling.

### Property and invariant tests

Property tests should establish that:

- Applying a clear mask never increases any plane's coverage.
- Changing only white policy never changes process coverage.
- Two mirrors return to the original orientation.
- Physical dimensions survive supported transforms.
- No output appears outside the printable box.
- Banded rendering matches full-frame rendering for the declared tolerance or exact equivalence where required.
- Job hashes change when any output-affecting input changes.
- A duplicate white-slot allocation never exceeds declared limits.
- Unsupported state cannot transition to production-ready state without evidence.
- An ambiguous attempt never causes automatic retry.

### Golden and integration tests

Maintain small golden fixtures for channel identity, overlap order, alpha behavior, opaque white, supplied masks, choke/spread, white allocation, screen phase, protocol framing, and unsupported settings.

Run the file-sink end-to-end workflow from PNG and mask import through preflight, render, inspect, encode, and retained artifact.

Run restart and fault-injection workflows around artifact creation, persistence, encoder output, and transport attempts.

Run Windows transport tests on supported Windows machines only when a staged device or controlled fake spooler is available.

### Physical bench tests

Maintain bench records for:

- Physical channel identity.
- Independent K, W, and required CMY behavior.
- Process/white deposition order.
- Orientation and film-side behavior.
- Scale and printable bounds.
- Feed, media path, guides, and eject behavior.
- Center and corner registration.
- White allocation across duplicate slots.
- Ramps, edges, fine detail, screening, banding, and wet load.
- Repeated output across sessions and after restart.
- Pressed transfer appearance, peel, stretch, and wash behavior for the selected finishing conditions.

Each record must include setup hash, mode hash, Recipe hash, target ID, ink, film, printer state, nozzle/feed observations, measurements, photographs where appropriate, and operator result.

### Acceptance gates

- **Gate 0:** preparation, hardware record, supplies, safe workspace, reference workflow, and artifact-recording procedure exist.
- **Gate 1:** native probe, verified mapping, candidate stream, independent channels, orientation, feed, scale, and repeated physical transfer exist.
- **Gate 2:** deterministic import, color, white, masks, transforms, screening, bounded bands, and final inspection pass.
- **Gate 3:** one validated mode and Recipe, preflight, portable jobs, recovery, selective reprint, and repeated quality evidence pass.
- **Gate 4:** clean installation, compatibility matrix, migrations, support bundle, and safe update/rollback pass.

## Out of Scope

- Broad printer-family support before the ET-8550 configuration is validated.
- Rolls, multi-lane production, industrial throughput, or automated production sorting.
- Full vector design editing or a replacement for a graphics application.
- Fluorescent, varnish, UV, or other channels outside the initial CMYK+W configuration.
- Generic N-color ICC profile creation as a first-release feature.
- Automatic printer cleaning, firmware updates, waste-counter operations, or ink servicing.
- Cloud queues, accounts, payments, subscriptions, DRM, and remote telemetry.
- Silent support for unsupported PNG features, HDR, APNG animation, unsupported PDF/SVG behavior, spot colors, overprint, or fonts.
- Claims of color accuracy, wash durability, or industrial quality outside measured ink, film, garment, press, cure, and viewing conditions.
- UI-first implementation that bypasses the native backend and rendering gates.
- Automatic retry after ambiguous printer submission.
- Runtime dependence on Digital Factory, AcroRIP, PrintFab, or another commercial RIP.

## Further Notes

The implementation plan remains the task-level execution source and this specification is the coherent product/build contract. The plan may evolve file names and exact dependency choices, but it must preserve the domain contracts and acceptance gates here.

The implementation plan currently contains a few historical formatting artifacts in example paths and commands. Before implementation begins, normalize crate names and command examples to the actual repository workspace naming. This is documentation cleanup only and must not change the architectural intent.

The project has no source code yet and no native ET-8550 protocol, channel mapping, feed behavior, or print quality has been physically proven. The first implementation work should therefore establish the workspace and bench record, then build the probe, file sink, diagnostic target, and artifact inspector before substantial desktop UI work.

If native independent process/white addressing cannot be demonstrated, the project must stop or be re-scoped rather than quietly becoming a commercial-RIP wrapper or prepress-only tool.

Commercial reference tools may be used for comparison, controlled reference prints, or research. Their feature lists and outputs must not be represented as evidence that Veylora supports the same behavior.

The project should create ADRs for consequential decisions such as the selected desktop UI framework, persistence format, ICC engine and redistribution strategy, ET-8550 protocol model, artifact format, and the first validated screening method.
